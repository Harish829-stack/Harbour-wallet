# BUGS_FOUND.md

**Status 2026-11-23: all 18 defects and all 16 observations are fixed** (see the Status line of each entry); every reproducing test is now a plain regression assertion. Product defects confirmed by the QA suite. When they were found, production code was **not** changed. Each bug has a test that reproduces it; that test is marked expected-fail with `expectKnownBug` (Go) / `knownBug` (JS): it is reported as SKIP with the evidence while the bug exists, and turns into a FAILURE once the product is fixed, so the marker gets removed. Run with `HB_QA_STRICT=1` to make every known bug fail.

Severity scale: **High** = fund loss or key/secret exposure possible · **Medium** = security control bypass, DoS of a shared service, privacy leak · **Low** = robustness / correctness without direct security impact.

## BUG-01 — `PUT /v1/me/addresses` is not atomic: a refused add still applies the removals and burns backfill budget
- **Status:** FIXED 2026-11-23. `PUT /v1/me/addresses` charges the backfill budget first, then runs removals and additions in ONE transaction (`store.ReplaceDeviceAddresses`, quota counted after removals); a refused request rolls back the removals and refunds the budget (`refundDaily`). `TestQAPutAddressesIsAtomic` is now a plain assertion.
- **Severity:** Medium (integrity of the user's tracked set; daily backfill budget can be exhausted by requests that were refused)
- **Where:** `apps/backend/internal/api/handlers.go:103-134` (`handlePutAddresses`): `RemoveDeviceAddresses` commits first, then `dailyCounter` charges the backfill budget, then `AddDeviceAddresses` can fail with `ErrQuota` (403 `quota_exceeded`). Removal and budget are not rolled back.
- **Impact:** A client that replaces addresses in one request (remove A, add B, C) and hits the quota loses A from tracking (history/notifications stop) although the request was refused; the backfill counter is charged for adds that never happened, so later legitimate adds can be refused with `backfill_quota`.
- **Reproduction:** `TestQAPutAddressesIsAtomic` (`apps/backend/internal/api/qa_integration_test.go`). Tier `max_addresses=1`; track `addr(1)`; send `{remove:[addr(1)], add:[addr(2), addr(3)]}` → 403 `quota_exceeded`, but `GET /v1/me/addresses` returns `[]` and `hb:bf:<tag>:<day>` = 3 (1 legitimate + 2 refused).
- **Suggested fix:** check quota before mutating (count after removals), run remove+add in one DB transaction, and charge the daily counter only after the add succeeded (or refund on failure).

## BUG-02 — Nested-null `eth_getLogs` topic filters pass the "address or topic required" guard on `/v1/rpc`
- **Status:** FIXED 2026-11-23. `filteredLogs` counts a filter only when it names at least one non-empty string (`hasConcrete`); `[null]`, `[null,null]`, `[""]` are wildcards and refused like no filter.
- **Severity:** Medium (provider budget abuse / heavy queries; the guard exists precisely to prevent unfiltered log scans)
- **Where:** `apps/backend/internal/api/handlers.go:251-268` (`filteredLogs`): a topic entry is considered a filter when its JSON is not `null`/`[]`; `[null]` (an OR-list containing only null) and `[null,null]` are treated as concrete filters, yet nodes treat them as wildcards.
- **Impact:** Any registered device can send `{"method":"eth_getLogs","params":[{"topics":[[null]],"fromBlock":"0x0","toBlock":"latest"}]}`; it is forwarded to rpc-gateway (observed body in the test). rpc-gateway still caps the block span, which limits the blast radius, but the policy "an address or a topic filter is required" is bypassed. The `/v1/gw/alchemy/<id>/rpc` route uses the same `filteredLogs` inside `boundedLogs` and is also bypassable (span still capped at 2000 blocks), spending the Alchemy key.
- **Reproduction:** `TestFilteredLogsRejectsNestedEmptyTopics` (unit, `internal/api/qa_unit_test.go`) and `TestQARPCNestedNullTopicsForwarded` (integration).
- **Suggested fix:** recursively require at least one non-null leaf value in topics (or a non-empty address).

## BUG-03 — `formatUnits` panics on negative decimals and does quadratic work on huge decimals
- **Status:** FIXED 2026-11-23. Decimals outside 0..77 are treated as unknown: `formatUnits` / `valueUSD` / notifier `displayAmount` return empty/0, padding uses `strings.Repeat`, and ingestion stores NULL (`store.ValidDecimals`, alchemy `decimalsOf`).
- **Severity:** Low → Medium (decimals come from provider/token metadata; a spam token with absurd `decimals` airdropped to a user makes every portfolio/history/tx read that includes it slow (quadratic string building) or, for negative values, panic and return 500).
- **Where:** `apps/backend/internal/api/read.go:81-103`. `for len(s) <= d { s = "0" + s }` is O(d²); with d < 0, `s[:len(s)-d]` slices out of range. Callers: `read.go:237, 395`, `media.go:68`, `send.go:292`. The same pattern is in `internal/notifier/notifier.go:213 displayAmount` (negative decimals panic: `TestQADisplayAmountHostileDecimals`); there it is reached only for native coins (decimals from chain config) and verified tokens, and a panic in the notifier consumer is not recovered. Decimals reach the DB unbounded from `adapters/sources/alchemy/webhooks.go:118 decimalsOf` and `store/indexer.go UpsertAsset/SetTokenInfo`.
- **Reproduction:** `TestFormatUnitsHostileDecimalsDoNotPanic`: `formatUnits("5", -1)` → panic `slice bounds out of range [:2] with length 1`; `formatUnits("1", 50000)` → 50 002-char string (scales quadratically: 1 000 000 decimals ran > 2 minutes).
- **Suggested fix:** clamp decimals to 0..77 at ingestion and in `formatUnits` (treat out-of-range as unknown), build the padded string with `strings.Repeat`.

## BUG-04 — `addWallet` lists the new keystore id before the vault write; a failed persist leaves a listed orphan keystore
- **Status:** FIXED 2026-11-23. New `VaultService.update(fn)`: the keystore and the wallet-id list are staged and written in the same `local.setMany` as the vault; deletions run only after the vault is saved. Used by addWallet, createWallet, persistImportedWallet, ledger add, removeWallet.
- **Severity:** Low (encrypted secret stays on disk for a wallet the user was told was not added; no exposure, but the wallet list and the vault disagree)
- **Where:** `apps/extension/src/background/modules/wallet.ts:281-290` (`addWallet`): `local.set(walletId, keystore)` and `local.set(KEYS.wallets(vaultId), list)` run before `vault.persist(state)`. Same order in `handlers/onboardingExtra.ts:persistImportedWallet`.
- **Impact:** if `vault.persist` fails (storage quota, IndexedDB abort, worker killed between writes) the response is an error, yet the keystore (encrypted secret phrase) stays in IndexedDB and its id stays in `wallet:wallets:<vaultId>`. Later key-schedule migrations re-key it (rekeyAll iterates that list), so it lives on indefinitely; `removeWallet` cannot remove it because it is not in the vault.
- **Reproduction:** `T-KEY-137` in `apps/extension/test/qa/vault-handlers.test.js`: wrap `vault.persist` to throw once → `addWallet` returns `PERSIST_FAILED`, vault has 1 wallet, `wallet:wallets:<id>` has 2 ids.
- **Suggested fix:** write the vault entry and the keystore in one `local.setMany` (both live in IndexedDB, one transaction), or remove the keystore and list entry on failure.

## BUG-05 — Re-auth grants are not atomically consumed: one grant can authorise two concurrent operations
- **Status:** FIXED 2026-11-23. `consumeReauth` runs on a module-level queue, so a grant is taken by exactly one caller.
- **Severity:** Low (the grant still requires the password/biometrics moments earlier; it only weakens "one-shot")
- **Where:** `apps/extension/src/background/reauth.ts:31-34` (`consumeReauth`): `session.get` then `session.remove`, two awaits with nothing serialising them.
- **Impact:** two messages sent back to back (e.g. two `revealSeed`/`addWallet`/`removeWallet` requests) both read the grant before either removes it, so both pass. The design (and PT-04/PT-08) assume a grant authorises exactly one sensitive action.
- **Reproduction:** `T-KEY-147` (`vault-handlers.test.js`): `grantReauth('reveal')`, then `Promise.all([consumeReauth('reveal'), consumeReauth('reveal')])` → `[true, true]`. The fake chrome.storage processes calls in issue order, as Chrome does.
- **Suggested fix:** serialise consume on a module-level promise chain (as `VaultService.serial` does) or keep the grant in worker memory with a synchronous take.

## BUG-06 — Vault read-modify-write handlers are not serialised: concurrent updates are lost
- **Status:** FIXED 2026-11-23. Every getState→persist handler now goes through `vault.update(fn)` on the worker-wide vault queue (wallet, account, rename, switch, remove, backupFinish, tokens, chain tokens, address book, dApp watchAsset, Ledger).
- **Severity:** Low → Medium (lost `backupFinish` flag, lost account/rename/token changes; a lost `removeWallet` can re-list a wallet whose keystore was deleted)
- **Where:** every handler that does `vault.getState()` … `vault.persist(state)` (`modules/wallet.ts` renameWallet/switchAccount/renameAccount/addAccount/switchWallet/removeWallet, `handlers/secrets.ts` backupFinish, provider `wallet_watchAsset`, smart-account state …). `VaultService.serial` only covers unlock/checkPassword/setPassword.
- **Impact:** last writer wins. Observed: `renameWallet`, `switchAccount` and `renameAccount` sent together → only the last persisted change survives.
- **Reproduction:** `T-KEY-135` (`vault-handlers.test.js`).
- **Suggested fix:** run every getState→persist sequence through the same module-level queue (e.g. `vault.update(fn)` that reads, applies `fn`, persists inside `serial`).

## BUG-07 — The QR-sync "5 wrong codes destroy the stage" limit is bypassed by parallel guesses
- **Status:** FIXED 2026-11-23. `qrCodeCheck(stageId, verify)`: code checks are serialised and the attempt is counted before scrypt runs (refunded when the code is right); exactly five wrong codes are checked, later ones get QR_EXPIRED.
- **Severity:** Low → Medium (the limit is the only brake on online guessing of the 6-character one-time code that decrypts the exported seed phrases; needs an internal extension page, so the attacker is local)
- **Where:** `apps/extension/src/background/qrStage.ts:33-39` (`qrWrongCode`: read `wrong`, then write `wrong + 1`) called from `modules/wallet.ts qrSyncImport` and `handlers/onboardingExtra.ts qrVerify/qrImportAll`, none serialised.
- **Impact:** N wrong codes sent together all read the same counter and all write the same `wrong + 1`; a batch of any size costs one strike. Observed: 50 wrong codes (5 batches of 10) were checked before the stage was destroyed; with larger batches the number of guesses within the 5-minute stage lifetime is bounded only by scrypt time.
- **Reproduction:** `T-KEY-133` in `apps/extension/test/qa/secrets.test.js`.
- **Suggested fix:** serialise code checks per stage (module-level promise chain) and count the attempt BEFORE running scrypt (increment first, then verify).


## BUG-08 — `eth_sendRawTransaction` from a site is forwarded to the Harbour backend without local validation
- **Status:** FIXED 2026-11-23. `eth_sendRawTransaction` from a site must be one 0x-hex string ≤ 256 KiB that viem `parseTransaction` decodes as a signed envelope; otherwise -32602 and nothing is sent to the backend (`checkRawTx`).
- **Severity:** Low (spec conformance + backend budget; no key or fund exposure — the wallet signs nothing)
- **Where:** `apps/extension/src/background/provider/service.ts:158-161` (`case 'rpc'` passes params through) → `core/harbour/fetchHook.ts:42-58` (`harbourRpc` calls `broadcastTx` with `params[0]` as long as it is a string).
- **Impact:** any page (no connection needed, `eth_sendRawTransaction` is a `rpc` kind) can make the worker POST arbitrary strings (up to 256 KiB) to `/v1/tx/<chain>/broadcast`, which first triggers device registration; the page gets `-32000` with a backend sentence instead of `-32602 Invalid params`. Other wallets validate the RLP envelope locally.
- **Reproduction:** `T-PM-001` in `apps/extension/test/qa/provider-port.test.js`: `eth_sendRawTransaction(["xxxx…"])` → `{"code":-32000,"message":"Harbour could not set up this device. Please try again later."}` and a fetch to the backend is recorded.
- **Suggested fix:** require `/^0x([0-9a-f]{2})+$/i`, a sane length and a decodable tx envelope (viem `parseTransaction`) before broadcasting; answer -32602 otherwise.

## BUG-09 — Two concurrent private-key copies both fail (offscreen port handshake overwritten)
- **Status:** FIXED 2026-11-23. `ensurePort` shares one pending handshake (`portReady`) between callers and resets it on failure or disconnect; concurrent copies both succeed.
- **Severity:** Low (availability of the copy feature; no secret is exposed — the copy simply fails)
- **Where:** `apps/extension/src/background/clipboard.ts:34-43` (`ensurePort`): a module-level single `onPort` resolver is overwritten by a second caller, and both callers call `chrome.offscreen.createDocument` while no port is connected yet.
- **Impact:** a double click on "Copy" (or two windows) makes the second `createDocument` throw ("Only a single offscreen document may be created") and the first caller's handshake promise is never resolved (its resolver was replaced), so it times out after 5 s with `COPY_FAILED`. Both requests fail; the user sees an error.
- **Reproduction:** `T-EXT-030` in `apps/extension/test/qa/ext-infra.test.js` (fake offscreen API that, like Chrome, refuses a second document).
- **Suggested fix:** keep one shared "port ready" promise (`portPromise ??= create…`) instead of a single resolver slot, and reset it on failure/disconnect.

## BUG-10 — On a new device, most accounts are silently left untracked (18 refs per address vs. a 40/day backfill budget)
- **Status:** FIXED 2026-11-23. `syncTracked` sends removals separately, then adds one address (all its networks) at a time with the active account first; on a quota refusal it stops and reports `untracked`/`limit`. The worker stores the status, `getAccounts`/`walletsDetailed` return a `tracking` notice and Home shows it; the sync is retried on the next wallet change. Backend quotas are unchanged (they are an abuse control).
- **Severity:** Medium (functional: balances, history and notifications missing for accounts the user holds; nothing tells them)
- **Where:** `apps/extension/src/core/harbour/data.ts:13-14` (`refsFor`: every EVM address is tracked on all 18 indexed networks) + `:67-75` (`syncTracked` sends the whole diff in batches of 100 and throws on the first refusal) vs. `apps/backend/config/api.yaml:15-16` (probation tier for the first 24 h: `backfills_per_day: 40`, `max_addresses: 100`; default tier 300/400).
- **Impact:** importing a seed with 3 used accounts on a fresh install: the first account (18 refs) is tracked, the next PUT (36 refs) is refused with 429 `backfill_quota`, the extension only logs a warning and retries on later wallet changes (each refused). The user sees empty balances/history for those accounts with no explanation. After probation, the default tier still caps a device at ~22 addresses (400/18) and ~16 new addresses per day, below the 30-wallet × N-account limit the extension allows. Related: BUG-01 (a refused PUT still applies its removals and budget).
- **Reproduction:** `apps/extension/test/e2e/quota.test.js` (real Go API + Postgres + Redis): `createWallet` + 2× `addAccount` → PUT statuses `200,429`, 1 of 3 accounts tracked, `getAccounts`/`walletsDetailed` carry no signal.
- **Suggested fix:** product decision — track only networks where the address has activity (or lazily on first view), size quotas to the per-address fan-out, and surface "tracking limit reached" in the UI; at minimum add what fits instead of failing the whole batch.

## BUG-11 — Send confirmation truncates the amount and the fee (debits can be shown smaller than what is signed, down to "0")
- **Status:** FIXED 2026-11-23. `fmtAmount` (send amount and fee) rounds UP at the last shown digit; balances use the new `fmtBalance` (rounds down).
- **Severity:** Low (display integrity; amounts below the 8th decimal)
- **Where:** `apps/extension/src/popup/wallet/send/lib.tsx:23-26` (`fmtAmount` cuts the fraction to `maxFrac` digits, i.e. rounds DOWN), used for the amount (`send/confirm.tsx:56`, 8 decimals) and the network fee (`send/parts.tsx:82, 96`).
- **Impact:** an amount of 123456789 wei is confirmed as "0 ETH"; a fee of 0.000042000001 ETH is shown as "0.000042". For a debit the screen must never under-state what the signature authorises (round up, or show "<0.00000001").
- **Reproduction:** `T-UX-027` in `apps/extension/test/qa/ux-sa-units.test.js`.
- **Suggested fix:** round debits up (ceil at the last shown digit) and show a "<" prefix when a non-zero value rounds to zero.

## BUG-16 — Indexer event consumers die for good if NATS is unreachable for > 5 s when the indexer starts
- **Status:** FIXED 2026-11-23. `Indexer.consume` retries a failed `Consume` with backoff (1 s doubling to 30 s) until the context ends; all six consumers use it.
- **Severity:** Medium (silent partial outage: the process stays up and healthy-looking while six event streams are no longer consumed)
- **Where:** `apps/backend/internal/indexer/indexer.go:183-221` and `internal/indexer/live.go:233-260`: each `ix.bus.Consume(...)` runs once in a goroutine; if it returns an error the goroutine logs "consume …" and exits, and nothing restarts it. `internal/events/events.go:74-79` (`NATS.Consume`) returns the error of `CreateOrUpdateConsumer`, which fails after JetStream's default 5 s API timeout when NATS is away (cmd/indexer's context has no deadline).
- **Impact:** after a NATS restart or a deploy where the indexer comes up first, the indexer stops handling `address.added` wake-ups (backfill falls back to 30 s polling), `address.history.more` (older-history requests), `address.nfts.sync` (NFT refresh), `tx.status.*`, `chain.*.activity.raw` (the live webhook path) and gap-fill requests until the process is restarted. Nothing fails loudly; only an ERROR line at start-up.
- **Reproduction:** `TestQAIndexerConsumersStartAfterLateNATS` in `apps/backend/internal/indexer/qa_resilience_test.go` (embedded NATS shut down for 7 s while `Run` starts; an `address.nfts.sync` event published after NATS returns is never handled).
- **Suggested fix:** retry `Consume` with backoff until ctx ends (or make `Run` return the error so the process exits and is restarted); the realtime bridge and notifier already return the error to their callers.

## BUG-18 — The vault cannot be saved once it holds about 8 wallets (stack overflow in the vault encryption)
- **Status:** FIXED 2026-11-23. `passworder` base64 converts in 32 KiB chunks (as `bytesToB64`); `passkey.b64url` too. 30 wallets and 2 MB payloads now round-trip.
- **Severity:** High (availability / data safety; the wallet advertises 30 wallets but every write of the vault fails from the 8th, so adding, renaming and switching wallets stop working; nothing is lost, but the user is stuck)
- **Where:** `apps/extension/src/core/passworder.ts:8` `const b64 = (u: Uint8Array) => btoa(String.fromCharCode(...u));` — spreads every ciphertext byte as a function argument; JavaScript engines cap the argument count (about 125,000 in V8), so `encrypt()` throws `RangeError: Maximum call stack size exceeded` when the encrypted vault is larger than that.
- **Impact:** `VaultService.persist` calls `encrypt()` for the whole vault state. Each wallet adds its addresses for every chain (about 16 kB), so the 8th wallet pushes the payload past the limit. The failing add has already written its keystore to storage (same ordering as BUG-04), leaving an orphan keystore. The same function is used for every vault write, so renames, account switches and backups fail too once the vault is that large.
- **Reproduction:** `T-KEY-119 (BUG-18)` and `T-KEY-119` in `apps/extension/test/qa/perf-ext.test.js`: `encrypt()` fails for 250 kB and 500 kB payloads, and `addWallet` fails at wallet 8 with "Maximum call stack size exceeded".
- **Suggested fix:** convert in chunks, as `core/provider/base58.ts` `bytesToB64` already does (`for (i += 0x8000) String.fromCharCode(...b.subarray(i, i + 0x8000))`), or use `Uint8Array.prototype.toBase64`. `core/passkey.ts:19` has the same pattern but only for small buffers.
